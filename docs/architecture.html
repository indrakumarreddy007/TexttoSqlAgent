HIGH-LEVEL DESIGN · v1.1 · KAGGLE DATA · OPEN-SOURCE STACK

Halcyon SQL Copilot: an agentic text-to-SQL service for governed enterprise data

Business users ask incomplete questions in English. The service works out what they meant, asks when it cannot safely guess, writes SQL against a messy multi-domain warehouse, and proves before running anything that the query obeys access, privacy and cost policy.

1Scope and goals

Halcyon Group is a fictional retailer. Its warehouse is built from two public Kaggle datasets: Olist Brazilian E-Commerce (9 related tables, about 100k orders, 2016–2018) for sales, customers, products, sellers and reviews, and IBM HR Analytics (1,470 employees) for the HR domain. On top of the raw data the build script adds the problems real warehouses have: cryptic legacy names, a deprecated table, soft deletes, customer history (SCD2), amounts in BRL that must be converted to USD, an April–March fiscal year, Portuguese category names, and synthetic PII generated with Faker.

Goals

  • Turn an underspecified question into a fully qualified, auditable request spec
  • Ask for clarification only when a guess would change the answer materially
  • Enforce governance deterministically: the LLM is never trusted to comply
  • Explain every answer with its SQL, assumptions and metric definitions
  • Measurable quality: offline gates before release, online monitoring after

Non-goals (v1)

  • Writing data (no DML/DDL, ever)
  • Charts and dashboards: the API returns tabular results only
  • Federated joins across warehouses
  • Training or fine-tuning models: prompting and retrieval only

Design principles

  1. The LLM proposes, deterministic code disposes. Every security property is enforced after generation by an AST-based policy engine. Prompts only reduce how often that engine has to reject a query.
  2. Least context. The model only sees tables and columns the caller's role may access. What it cannot see, it cannot leak or hallucinate.
  3. Semantics live in metadata, not prompts. Metric definitions, synonyms, fiscal rules and defaults sit in a versioned catalog and glossary. Prompts reference them.
  4. Every step is a typed contract. Pydantic models connect the stages, so each one can be swapped, tested and evaluated on its own.
  5. Fail closed. On parse failure, policy ambiguity or a timeout, the service refuses with a reason. It never falls back to unchecked SQL.

Orchestration with LangGraph

The pipeline is a LangGraph StateGraph over a typed AgentState. LangGraph supplies what a hand-written loop would otherwise have to build: conditional routing, bounded cycles, pausing for a human, durable per-conversation state, streaming, and node-level tracing. Guardrail and policy nodes are plain Python functions that call the framework-free src/sqlagent/guardrails package. The security boundary therefore doesn't depend on LangGraph, and the same engine backs /v1/validate.

S0

Ingress and identity

The gateway authenticates the caller and resolves a UserContext of user ID, role, regions and clearance from trusted claims. Anything the user writes in the question (“I'm the CFO”) is ignored for authorization. A conversation ID ties clarification turns together. Pending specs live in a memory store with a TTL.

Output
UserContext, request_id, conversation state
Fails
401/403, 429. No agent work is done.
S1

Input guard

Cheap checks run before any LLM call: length and character limits, language detection, and pattern rules for prompt injection (“ignore previous instructions”, embedded SQL keywords such as DROP/GRANT, “show the system prompt”). An optional small classifier separates off-topic from data questions. A positive hit does not need to be perfect, because S6 is the real barrier. The guard records a risk_flags list that tightens later behaviour, for example no retries and refusal on any policy violation.

Output
Sanitised question, risk_flags
Type
deterministic optional classifier
S2

Context retrieval (schema linking)

The warehouse has too many tables to fit in a prompt, and most are irrelevant. Hybrid retrieval does three things:

  1. Lexical BM25 over table and column names, descriptions and synonyms, so “client” and “account” find CUST_MSTR_V2. An optional embedding index can be added later.
  2. Glossary matching links terms such as “revenue”, “last quarter” or “active customer” to certified metric definitions and their default rules.
  3. Join-path expansion over the catalog's foreign-key graph adds the bridge tables needed to connect the hits.

Results are filtered by role before ranking, so denied tables never reach the prompt. Deprecated tables are dropped and their replacement is noted. The top k verified question→SQL examples are added as few-shot examples.

Output
SchemaContext (tables, columns, joins, metrics, examples) with a token budget
Type
deterministic
S3

Clarify and fully qualify

The LLM fills a strict JSON schema called QualifiedRequest. It has metrics (IDs of certified metrics), dimensions, filters, time window (calendar or fiscal, with resolved start and end dates), grain, ordering and top N, currency, assumptions and ambiguities. Each ambiguity is labelled with a type:

AmbiguityExamplePolicy
Metric“top customers”: by revenue, orders or margin?blocking unless the glossary has a default for the term
Time window“last quarter”: fiscal or calendar? Relative to when?default to fiscal and the data's as_of_date, and state it
Entity“São Paulo”: customer state, customer city or seller location?Default from the catalog role of the column, otherwise blocking
Grain“sales by month” across yearsDefault per glossary
ScopeInclude freight? Canceled orders?Certified metric rules decide. Never asked.
CurrencyAmounts are stored in BRLDefault reporting currency is USD at the daily BRL→USD rate

A deterministic resolver then turns relative dates into concrete ones from the fiscal calendar, checks that every metric ID exists, and decides: ask (if any blocking ambiguity is left), or proceed and list each default it applied as an assumption. Clarifying questions are multiple-choice where possible, so the reply resolves cleanly. At most 2 rounds are allowed. After that the agent states its best interpretation.

{
  "intent": "ranking",

  "assumptions": ["'last quarter' = last complete fiscal quarter as of 2018-08-31",

S4

SQL generation

The second LLM call works from the qualified spec, not the raw question. The prompt contains: the role-scoped schema in compact DDL with descriptions, certified metric SQL fragments to be used verbatim, join paths, few-shot examples, the dialect, and house rules (fully qualified names, explicit column lists, ISO dates). The output is JSON {sql, tables_used, rationale}. Splitting qualification from generation is the main architectural choice. It makes clarification testable on its own, and it shortens the generation prompt.

Output
CandidateSQL
Type
LLM
S5

Static validation

The candidate is parsed with sqlglot in the target dialect. A parse error is a correctable violation. The validator checks the following, each with a stable violation code (V###):

  • Exactly one statement, and the root is SELECT, UNION or WITH … SELECT.
  • No forbidden nodes anywhere in the tree: DML, DDL, PRAGMA, COPY, ATTACH, SET, table functions such as read_csv, or system functions.
  • Every table resolves to a catalog entry; CTE names are excluded. Every column resolves, using sqlglot's qualify with the catalog schema, so hallucinated columns fail here with a helpful message.
Type
deterministic
S6

Policy enforcement and rewrite

This step is the security boundary. It is detailed in section 4. It validates (denied tables and columns, deprecated tables, missing mandatory filters, cartesian joins, row-level aggregation of sensitive data) and then rewrites. Each base table is wrapped in a policy view that applies row filters and column masks, and a hard LIMIT is enforced. The rewritten SQL is what runs and what the audit log stores.

Type
deterministic security boundary
S7

Cost check

EXPLAIN on the rewritten query gives an estimated cardinality and scan size. These are compared with the role's budget. A query over budget is sent back with a hint, for example “add a state filter on ops.geo”. On Snowflake or BigQuery, a dry run supplies bytes scanned.

Type
deterministic
S8

Bounded self-correction

Correctable violations (parse error, unknown column, missing filter, over budget) go back to S4 as structured feedback: code, message and AST location. There are at most 3 attempts. Non-correctable violations (denied table or column, a PII request, a write) end the turn with a refusal. Retrying them only invites the model to find a workaround. When the input guard raised a risk flag, retries are disabled.

S9

Sandboxed execution

The query runs on a read-only connection under a service account with SELECT on the curated schemas only. Additional limits: external file and network access are disabled, configuration is locked, there is a statement timeout (interrupt after 30s), and rows and bytes are capped. A failed execution, such as a type error, is fed back once through S8.

S10

Output guard and answer

The output guard checks the result itself:

  • Group sizes below the threshold (k = 5) are suppressed for sensitive domains.
  • A regex and entropy scan catches PII that leaked through derived expressions.
  • Empty results get a diagnosis, such as “no orders in that window for EMEA”.

The answer contains the result table, the final SQL, assumptions, metric definitions with their owners, the tables used (lineage) and a short summary. The summary is generated only from the returned rows, and numbers in it are checked against the result.

S11

Audit and telemetry

Every step writes an event: inputs, outputs, prompt version, model, tokens, latency and violations. The events form one trace per request, keyed by request_id. The trace is the raw material for online evals and for regression cases.

Rewrite example: row-level security

The LLM wrote the first query. The engine produced the second. The model never needed to know about regions.

-- candidate
SELECT c.cust_nm, COUNT(*) AS orders
FROM sales.ord_hdr h JOIN crm.CUST_MSTR_V2 c ON c.cust_id = h.cust_id AND c.is_current
WHERE h.is_deleted = FALSE GROUP BY 1 ORDER BY 2 DESC

-- enforced
SELECT c.cust_nm, COUNT(*) AS orders
FROM sales.ord_hdr AS h
JOIN (SELECT * FROM crm.CUST_MSTR_V2
      WHERE cust_state IN (SELECT state_cd FROM ref.region WHERE region_cd IN ('SE'))) AS c
  ON c.cust_id = h.cust_id AND c.is_current
WHERE h.is_deleted = FALSE GROUP BY 1 ORDER BY 2 DESC
LIMIT 1000
Why rewrite rather than ask the model to add filters? A rewrite is applied to every table occurrence, including inside CTEs, subqueries and self-joins, whatever the model wrote. Asking the model gives a probabilistic guarantee, and probabilistic access control is not access control.

The catalog holds, per table and column: a description, owner, sensitivity class, synonyms, join keys, size class and deprecation. Rollout

  • Shadow mode: a new prompt or model runs next to production. Results are compared and nothing is shown to users.
  • Canary at 5% per role, with automatic rollback on gate breach
  • A/B on prompt versions. Guardrail metrics are invariants, not trade-offs.

Signals

  • Implicit: re-ask within 2 minutes, abandoned clarification, SQL edited by the user, result exported
  • Explicit: thumbs with a reason code
  • Rates: clarification, refusal and self-correction, with retries per request

Quality sampling

  • 1–5% of traces scored daily by an LLM judge (correctness against the spec, faithfulness of assumptions), run as Langfuse evaluators or as a batch job over the audit log
  • Judge calibrated against a monthly human-labelled sample (agreement κ tracked)

Drift and safety

  • Schema drift: catalog vs. warehouse diff alerts
  • Glossary gaps: frequent unresolved terms surface as candidate glossary entries
  • Spikes in policy-block rate per user (probing) go to security
